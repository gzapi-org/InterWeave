# Separate config, identity, mutable state, cache, and runtime endpoints

**Status:** Accepted; endpoint state classes clarified by ADR-0030.

## Context

P2P identities are security-sensitive and multiple local profiles must never share them accidentally. Model B also distinguishes persistent endpoint configuration from ephemeral endpoint leases/presence.

## Decision

Use profile-specific platform directories for normal configuration (including endpoint definitions/default/ACLs), private identity key, mutable daemon state/logs, replaceable peer cache, the profile lock (in the state directory), and the runtime sockets (A 2026-09-28).

Endpoint leases and remote endpoint-directory results are runtime state only and are not persisted as authoritative configuration. Repository examples contain no private keys/secrets.

The profile lock is one file in the STATE directory (`<state>/profile.lock`, owner-only), reachable offline with no runtime directory, held exclusively by the daemon for its lifetime and by `transportctl identity backup`/`restore`; it is released, never unlinked, so no two processes can lock different inodes at one path. The runtime sockets are disposable and removed only by the lock holder, and only when the path holds a socket owned by the daemon's uid; anything else at that path is fatal. Endpoint enable/disable/default changed over administrative IPC is a RUNTIME OVERLAY over the configured state, never written back to `config.yaml`, and does not survive a restart. (A 2026-09-28)

Trust changed over administrative IPC (`admin.trust.set`, ADR-0037) is a PERSISTED OVERLAY (A 2026-10-07, the owner's decision on rust-ui-dev's finding that a revocation was undone by a daemon restart): the composition keeps the operator's trust deltas — through a store it takes at construction, which the daemon and the embedded runtime (Android) each supply under their own state directory, so the rule binds every production binding — in the STATE directory as `<state>/trust-overlay.json` — owner-only, refused at startup when it is not owned by the daemon's uid or is readable or writable by anyone but its owner (the key's rule, no group or other bit) — holding exactly two lists: `added`, the peers allowed beyond `config.yaml`'s `trust.allowed_peers`, and `revoked`, the configured peers revoked. The effective allowlist is (configured ∪ added) ∖ revoked, derived at startup before the first connection is admitted; an effective allowlist larger than `PeerTrustPolicy::MAX_ALLOWED_PEERS` is FATAL at startup, never truncated. The overlay is a delta against the configuration the daemon started with, and it is NORMALISED when loaded — a peer in both `added` and the configuration leaves `added`, a peer in `revoked` and not in the configuration leaves `revoked`, and the file is rewritten when that changed anything — so an operator who edits `config.yaml` between restarts gets the union they expect and no stale entry can undo a later edit. A set is one of four moves on the normalised lists: allow a configured peer removes it from `revoked`; allow any other peer adds it to `added`; revoke a configured peer adds it to `revoked`; revoke any other peer removes it from `added`. The file is written whole to a temporary file and renamed into place BEFORE the new policy is published to the runtime and BEFORE the set is answered, so a set answered `ok` survives a crash and a set whose write fails changes nothing; when the publish fails after the write (the substrate gone), or the write's directory sync fails after its rename, the previous overlay is restored through one path before the set is answered failed; if that restore fails before its own rename, the overlay is left AHEAD of the runtime — the set is answered `Internal`, audited `failed`, a warning logged — and it takes effect at the next start whichever way it went: for a revocation the conservative direction, for an allow a peer the operator was told is not allowed becomes allowed at the next start. Two filesystem failures in a row reach it and no input does; while the overlay is ahead, an allow the running policy's bound admits but that would put the overlay past `MAX_ALLOWED_PEERS` at the next start is refused `InvalidArgument`, audited `refused`, nothing written, so the ahead state never grows into a fatal start; the answer, the audit outcome and the warning make the state visible, and a running daemon is not stopped on a disk fault (the alternative, failing the runtime so the restart is deliberate, was rejected 2026-10-07: it trades one surprise for another); `config.yaml` is never written. The overlay is mutable state in its own class (`configuration.md`): authorisation, not configuration — backed up with the profile, and never deleted to "reset", since deleting it re-allows every peer the operator revoked. A present overlay that does not parse, or names a peer in both lists, is FATAL at startup, never skipped; a normalisation rewrite that fails at load is FATAL too, since a stale entry left on disk could undo the operator's next `config.yaml` edit — a skipped overlay would silently re-allow every revoked peer. `admin.trust.list` reports, on a connection that negotiated IPC 2.3 or later, `persisted: true` on every row and each row's `source` (`configured | administered`; a normalised overlay has no peer in both); below 2.3 the 2.1 row shape is served unchanged (ADR-0017 A 2026-10-07: a closed result shape widens behind a new minor while the old shape is served below it). Endpoint changes stay the runtime overlay above; the same file shape is available to them when their carried item is taken (plan §20).

## Alternatives considered

Single loose state directory; key in YAML; environment-only identities; project repo key; persist endpoint leases/presence across restart. For trust (2026-10-07): the daemon writing `config.yaml` (configuration would have two writers, and a comment-stripping rewrite of the operator's file); the client re-applying its own changes at reconnect (a revocation would be undone for the window before the client reconnects, and only while that client exists); leaving trust a runtime overlay (the finding itself).

## Consequences

Backup/deletion rules stay clear: endpoint config may be backed up; the trust overlay is backed up with the profile and is never deleted to reset, because deleting it re-allows every revoked peer (A 2026-10-07); leases/directory cache are recreated. Daemon restart preserves PeerId but all local endpoint routes start offline until clients reconnect; the trust allowlist restarts as the operator last left it, configuration plus overlay (A 2026-10-07). The optional identity recovery record is stored **outside normal profile configuration/state** and is treated as private-key-equivalent offline backup material.

## Security implications

Private key remains owner-only, and the directory that holds it — like every private file's directory: the trust overlay's, the human store's, the profile lock's — is judged with its ancestors (A 2026-10-08): every component of the directory's canonical path, from its parent up to `/`, is owned by root or by the daemon's effective uid and carries no group- or other-write bit (a sticky directory, still root's or ours, accepted whatever its write bits), every symbolic link the configured path traverses is owned by root or ours and sits in a directory meeting the same rule, its ancestors with it, and the opens named below use the path that was resolved. That is the precondition under which the operating system makes a swap of the directory impossible — in a sticky directory an entry is renamed only by its owner, the directory's owner or root, and the rule already requires that directory to be root's or ours — so no account but root and the daemon's can rename the directory, or repoint a link on its path, between the check and the open, and no check-then-open race remains to argue about. The configuration file's directory is judged the same way — its ownership and write bits and its ancestors', not an owner-only mode, since `config.yaml` is not secret — because `config.yaml` names the key path and the configured allowlist, and an account that could replace it would choose the key's directory and admit its own peer; and `config.yaml` itself is opened without following a final link and refused unless it is owned by root or ours with no group- or other-write bit (readable by others is allowed: it is not secret). The resolved-path open holds for the key, read and write, the two private writers (the overlay's write among them), the overlay's read, both locks and `config.yaml`; the human store opens its file by its configured path under the directory `HumanClientLock` judged — the carried item (rust-ui-dev's). The walk runs once, in `require_private_dir`, the `profile-config` helper the two `profile-config` private writers call and the identity loader and both locks reach, on every call; an ancestor or link that breaks the rule, or cannot be inspected, is refused where the directory's own rule refuses, naming the failing ancestor or link, its owner uid, its mode and the rule it broke; no configuration setting relaxes it — a refused layout (a group-writable or shared home, an ancestor owned by a deploy account other than the daemon's) is fixed with `chown`/`chmod`, which the refusal says. Standard v1 key-at-rest mode is filesystem-only; ADR-0038 records an explicit optional v2.x encrypted-key path rather than leaving it as an unnamed revisit. Recovery phrases are never written to config/state/cache/logs and never cross daemon IPC. Endpoint cache/leases cannot masquerade as durable authorization. The trust overlay IS durable authorisation (A 2026-10-07): owner-only, refused when not the daemon's own or readable or writable by anyone but its owner, fatal when unparseable, never skipped or truncated, and deleting it undoes every revocation — the backup table says so. Logs sanitize peer/endpoint identifiers as configured.

## Operational implications

Profiles migrate intentionally. Runtime sockets/leases/cache are disposable. Config schema v2 is the source of configured endpoint names/policies.

## Implementation implications

Atomic config writes, OS-specific directories, explicit profile initialization. Never auto-regenerate existing profile key; never restore old endpoint lease ownership from disk. Identity backup/restore follows ADR-0033 and requires offline exclusive identity-file access plus atomic owner-only writes.

## Revisit conditions

Revisit for HSM/keychain identities or stronger local endpoint-client authentication while preserving logical separation.
