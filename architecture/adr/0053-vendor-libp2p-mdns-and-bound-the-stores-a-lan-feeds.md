# Vendor libp2p-mdns and bound the stores a LAN feeds

**Status:** Accepted

## Context

`DISCOVERY-CONFORMANCE.md` guarantee 5 says provider state and emitted batches are bounded, and the mDNS provider's are (`crates/discovery/mdns`: 256 peers, 8 addresses per peer, a 120 s observation TTL). The crate beneath it is not. `libp2p-mdns` 0.49.0, the version `libp2p 0.57` locks, keeps three structures that the multicast domain fills with no cap, read in the pinned source on 2026-09-25 (p2p-network-dev from the registry, architect-cto from the tarball): `Behaviour::discovered_nodes` (`behaviour.rs:142`), a `SmallVec` of every (peer, address, expiry) heard, searched linearly on every insert (`:328-331`) so CPU is quadratic in what the LAN announces, each entry expiring on the ANNOUNCER's own TTL (`iface/query.rs:184`); per interface, `InterfaceState::discovered` (`iface.rs:105`), a `VecDeque` extended with every response's pairs (`:305-306`) and pushed back to its front whenever the behaviour's `mpsc::channel(10)` (`behaviour.rs:168`) is full (`:257`); and per interface, `InterfaceState::send_buffer` (`iface.rs:97`), which every received QUERY extends with a response (`:290`), each entry becoming a packet this node multicasts. An unsolicited response is accepted: a packet with no questions is a response (`iface/query.rs:57`), matched against no query this node sent. Loopback interfaces are skipped (`behaviour.rs:287`), so a flood arrives over a real interface as unsolicited multicast responses, which the crate accepts by design. Measured as released on 2026-09-25 (SPIKE-010's flood row, `spikes/spike-010/harness/REPRODUCTION-2026-09-25.log`): the store held 65,536 of 65,536 distinct announcements, the time inside `poll` per new record rose from about 3 µs at 256 to about 213 µs at 65,536 — quadratic in the total — and resident memory grew by about 14.5 MB.

The mechanism ships gated off, and since PR #111 (`MdnsScope`, f85dd27) nothing the crate hears reaches a dial or a book, so the exposure is memory, CPU and one amplification path — a query flood is answered packet for packet onto the LAN — from hosts on the same multicast domain. `DISCOVERY-CONFORMANCE.md`'s Decision 2026-09-25 recorded that as the exception CLAUDE.md §6 requires, time-boxed: the stores are bounded before the mDNS deadline reads MET (plan §14). Nothing in this repository can bound them from outside the crate, and the same reading found the crate's failure signals stop inside it: a failed bind or multicast join at interface-up is logged and produces no event; a receive error other than `WouldBlock` ends that interface's task silently; a send error is logged and skipped. `providers/mdns.md` §Failure needs those as events to report degraded. p2p-network-dev chose vendor-and-cap on 2026-09-25 and the owner ordered the work started the same day; ADR-0051 opened the route for one crate, and the third_party README says every vendored directory is the subject of an ADR. This is that record for the second.

## Decision

1. **The workspace builds `libp2p-mdns` from `third_party/libp2p-mdns/`**, the 0.49.0 crates.io tarball (sha256 `9e82fb6db53f8ba1642bc0695ee589f7bcc1ff9028a9d068a88ee0db5b94667f`), selected by a `[patch.crates-io]` entry in the root `Cargo.toml`, under ADR-0051's route: the copy is the tarball minus its packaging files, plus the upstream `LICENSE` and one recorded diff, `INTERWEAVE.patch`, which carries every patch this repository holds against the crate; the first commit of the vendoring branch is the verbatim copy, so the patch is exactly the diff; every file is listed in `tools/checks/license_exempt.txt` with licence, holder, version and checksum, `third_party/README.md` gains the row, `check_vendored_advisories.sh` covers the crate by finding its manifest, and every libp2p bump re-vendors the tarball, re-applies the diff and re-records the checksum (ADR-0051 Decisions 1, 2, 5–8 apply unchanged; they are not restated here).
2. **Every store the multicast domain feeds has a cap, and past the cap a record is dropped and counted, never stored.** `Behaviour::discovered_nodes` takes the provider's SHAPE, not only its count (corrected 2026-09-25, PR #112's third review): at most `MAX_PEERS` distinct peers and at most `MAX_ADDRESSES_PER_PEER` addresses per peer — 256 and 8 as `crates/discovery/mdns` defines them, both drift-checked against those constants the way the driver's batch bound already is — so the crate never remembers a record the provider would refuse, and never fewer than it would keep — WHILE NO REFUSED RECORD IS HELD (qualified 2026-09-25, the last blind review of PR #112): the class boundary of ADR-0052 sits at the driver's learn site, after the crate has stored, so a record whose address the boundary refuses (a spoofed link-local source, say) occupies a crate slot and no provider slot; under a flood of such records the crate can evict or refuse an admitted record while the provider still has room. Consumer consistency is unaffected — the provider only ever sees admitted records — and the effect is not measured; the code says the same beside `make_room_for` (2af9f007). A count-only cap of 256 × 8 = 2048 records of any shape, which this rule first said, was equal in count and not in shape: a flood of single-address peers filled the provider at 256 while the crate went on to 2048, the 1,792 records past that were ones the provider had refused, and evicting one of them freed nothing in the provider — so a legitimate replacement was refused there and not re-reported while the crate's dedup refreshed its expiry, a wait the clamp bounded to one TTL and no reporting order could remove; the invariant "the provider stays consistent with the crate at capacity" had reopened three times on that PR before the premise was found. Per-peer accounting is one count map beside the store. Per interface, `discovered` holds a small constant sized from the behaviour's channel of 10 (proposed 64) and `send_buffer` a small constant of packets (proposed 16); p2p-network-dev fixes the two numbers in the patch and records them in `resource-limits.md`. When a bound is hit — the peer count, or one peer's address count — the soonest-expiring record within that bound is evicted, so each eviction frees exactly the slot the provider would free, and the reporting order (an eviction's `Expired` before its replacement's `Discovered`, batches netted before they are queued) then keeps provider and crate consistent rather than merely close.
3. **The announcer's TTL is clamped at intake to the provider's observation TTL** (`OBSERVATION_TTL_MS`, 120 s). The provider forgets a record after that long whatever the announcer said, so a longer crate entry serves nothing but an attacker: without the clamp a flood announced with a very long TTL is never the soonest-expiring and evicts every legitimate short-lived record under rule 2. The TTL this node ANNOUNCES for its own records (`ttl_ms`, 6 min by default) is a different number and is unaffected — what this node says is not what it believes. **The interval this node QUERIES at sits below the clamp, or a quiet LAN churns** (added 2026-09-25, PR #112's blind review F6): with the released defaults — a 300 s query interval against the 120 s a heard record now lives — a peer on a two-node LAN is discovered, forgotten at 120 s and rediscovered at the next exchange, the churn `MdnsSettings::validate`'s own comment names as a defect. So the default query interval is 90 s, three quarters of the clamp (RFC 6762 §5.2's cache-maintenance point), and `validate` requires `query_interval_ms` below `MAX_RECORD_TTL` beside its existing bound below the announced TTL: a profile that sets the interval above the clamp is refused, not churned. Accepting the churn was declined — a peer re-answers whenever anyone queries, so on a busy LAN the churn hides and on a quiet one it is the whole experience. Lands on PR #112 with the clamp that made it necessary.
4. **A given record is multicast on a given interface at most once per second** (RFC 6762 §6's literal: a responder MUST NOT multicast a record on an interface until a second has passed since it last did). The slot is PER RECORD, not per interface — corrected 2026-09-25 from PR #112's blind review: one slot per interface would let a service-discovery meta-query at one packet a second take the slot every second and starve this node's peer records for as long as it lasted. Per record, what this node sends in reply is bounded by the size of its own record set — per interface per second, whatever is asked; as built, the slot is per ANSWER, of which this node has two (the peer answer, PTR plus its TXT records, and the service-discovery answer), which is per record or stricter ACROSS answers (the PTR target is random per answer) and two timestamps per interface. WITHIN one peer answer it is not (A 2026-09-25, after PR #112 landed): an interface address carrying more than 29 relevant addresses answers in ceil(A/29) packets sent back to back after one rate check, each repeating the PTR, because a receiver reads a packet's TXT records only through a PTR in that same packet — upstream's behaviour, pre-existing and kept, since removing the repetition breaks discovery; the trigger is local configuration, no remote host can cause it, and the output stays bounded at one answer and at most 16 packets per second per interface address. Queries arriving inside a record's second are counted and not answered, so a query flood cannot make this node flood the LAN; the cap on `send_buffer` in rule 2 is the backstop behind it, not the mechanism. The slot is per interface ADDRESS, so a host with K addresses answers K times per second; that multiplier is local configuration, accepted and recorded here so nobody reads the bound as global.
5. **Two additive public events, and nothing else on the crate's event type.** `Event::InterfaceFailed { address, reason }` is emitted where the crate today logs and moves on: a failed bind or multicast join when an interface comes up, a receive error that ends an interface's task, a send error; `address` is this node's own interface address, never a peer's. `Event::WatcherFailed { reason }` (added 2026-09-25, PR #112's blind review) is emitted when the interface watcher itself returns an error after start, which the crate also only logged — a second variant rather than `InterfaceFailed` carrying an unspecified address, because a sentinel in a field documented as an interface address is a meaning smuggled into a value, and a match arm is the honest shape. It is emitted ONCE, and again only after the watcher has yielded an `Ok` event: `if-watch` 3.2.2 returns `Err` on every poll once its netlink connection has gone — read in `netlink-proto` 0.12.2 and `if-watch` 3.2.2 by PR #112's last blind review (2026-09-25), not yet reproduced — the crate's `while let` over it then never exits, so the Swarm task spins and no event is ever returned in that case, and one event per `Err` would besides grow `pending_events` without bound — local state, not remote-fed, but rule 2's discipline holds for it all the same. **So the patch also stops the spin** (decided 2026-09-25; built on PR #112 the same day, a0dfc1d7, after the automated review of 05f86ce0 rated the spin P1; rule 8 lists it): a watcher that returns `Err` on two consecutive polls is dead — the loop stops polling it, `WatcherFailed` is emitted once and returned, and the behaviour keeps serving the interfaces it already has; recovery is the runtime's — re-running `mdns_driver::build_behaviour` when `MdnsWatcherFailed` arrives, whose whole failure surface is the watcher's construction — and that rebuild is NOT yet built (A 2026-09-25, after PR #112 landed): it is p2p-network-dev's, in the next mDNS change beside rule 8's accessor and rule 10's refresh. Until it lands, a node that loses its interface watcher sees no new interface and does not tear down one that goes away — the task for a vanished address is never aborted, keeps its sockets and its rate slots, keeps answering, and its failing sends report `InterfaceFailed` — until the process restarts; `MdnsWatcherFailed` is the first signal, those `InterfaceFailed`s the later ones. The `Provider` trait's `Watcher` type is the seam a test ends a watcher through, so the stop is measured, not asserted: a test watcher that errors on every poll is polled twice over five polls of the behaviour and one event comes back; with the stop removed the same watcher is polled 1,006 times. The runtime's mDNS arm surfaces the two as `SwarmEvent::MdnsInterfaceFailed` and `SwarmEvent::MdnsWatcherFailed` — `MdnsScope` passes the crate's events through, as it does the interface watcher's `MdnsUnavailable` — and the provider's degraded state is set from that event by Stage 12's composer, where provider health lives (`providers/mdns.md` §Failure; corrected 2026-09-25 from "`MdnsScope` maps it onto degraded", which named the wrong layer). Whether to re-create a failed interface is the runtime's decision, not the patch's. The patch changes no existing field or variant, as ADR-0051 Decision 3a did.
6. **Unsolicited responses stay accepted.** RFC 6762 §8.3 makes gratuitous announcements the protocol, and refusing a response this node did not query for would break discovery of a peer that announced first. The defence against a flood of them is rules 2–4, not a match against sent queries; recorded so that no later reader "fixes" it.
7. **Every drop is counted by store and readable outside the Swarm task**, on the runtime handle where the address-class refusals already are (PR #111, f7baced): records evicted from `discovered_nodes`, records dropped from a full `discovered`, packets dropped from a full `send_buffer`, queries not answered under rule 4. No address is logged for any of them (ADR-0052 rule 5's discipline holds for a store the boundary sits behind).
8. **Nothing else is patched.** The patch is rules 2–5 and one line of discipline (added 2026-09-25): the crate's two INFO lines that log every record it inserts or expires WITH ITS ADDRESS (`behaviour.rs`, "discovered peer on address" and "expired peer on address") lose the address, keeping the peer id — they run before the driver's class boundary, so an address the boundary then refuses was written to the log against ADR-0052 rule 5's discipline, and under a flood they were one line per record. Two more items, decided 2026-09-25 after PR #112's last review: the dead-watcher stop of rule 5, built on that PR (a0dfc1d7) together with one additive `pub use` of the `Provider` trait — the seam the stop's test reaches from `crates/transport/libp2p/tests/`, since a vendored crate's own tests do not run in CI, and a trait that already bounded the public `Behaviour<P>` — and, for the next mDNS change before the deadline reads MET, one additive accessor over the live records — `(PeerId, Multiaddr, expiry)` — that rule 10's refresh reads, because `discovered_nodes()` yields peer ids alone. A further change to this crate is an amendment to this record before it is written.
9. **The order of work, and what MET needs.** First the flood harness against the UNPATCHED crate, committed with its numbers — the adversarial coverage the 2026-09-25 exception owed, injected over a private interface as unsolicited responses because loopback is skipped; then the verbatim vendor commit; then the patch; then the harness flipped to assert the record-store cap, the per-interface discovered cap, the TTL clamp and the once-per-record-per-second rule. The `send_buffer` cap is the backstop behind rule 4 and is reached only by local configuration — one answer fills it when an interface address carries 465 or more relevant listen addresses (17 packets), which no remote host can cause — so it is asserted PRESENT (the constant and its drop counter, drift-checked) and exercised by no wire test (settled 2026-09-25; the first wording, "unreachable while rule 4 holds", overstated and is corrected A 2026-09-25, after PR #112 landed — `crates/transport/libp2p/tests/mdns_bounds.rs` still carries it in its header and beside its assertion, and follows in the next mDNS change). **Where the assertions run (decided 2026-09-25, after the measurement).** A packet reaches the crate only on a domain this repository makes: the crate skips loopback, and the host's shared interface does not loop multicast back to a socket joined on it (measured, 2 s on 5353 and 5354) — while an unprivileged user network namespace (`unshare -rn`) with a dummy multicast interface carries it, needs no root, and is a domain CHOSEN rather than inherited, which is SPIKE-010's rule. So the cap assertions are tests in `crates/transport/libp2p/tests/`, the lowest layer that sees both the vendored crate and the workspace's features (ADR-0051's placement), that re-execute themselves inside that namespace and FAIL, never skip, where user namespaces are unavailable. Ubuntu 24.04's default AppArmor restriction on unprivileged user namespaces means the CI runner needs one workflow step to lift it; that step is devex-tooling's — p2p-network-dev requests it naming the test, devex-tooling supplies the commit onto the vendoring branch, and the branch does not open as a pull request without it: a test that fails for want of the step is the design working, not a reason to skip. The first run's record is the SPIKE-010 harness — the same namespace, the same injection, the log committed beside its pin (98cee3a) — and `SPIKES.md` carries the flood row; from then on the executable test is what MET rests on, and the log is what a later reader compares a new run against. No packet-injection seam is patched into the crate: a packet path that exists only for tests would be a code path a production caller could reach. Naming an existing trait — rule 8's `pub use` of `Provider`, which already bounded the public `Behaviour<P>` — adds no code path and is not that (reconciled A 2026-09-25, after PR #112 landed). The mDNS deadline (plan §14) reads MET when rules 2–5 and 10 are in the tree with those tests green in CI and `DISCOVERY-CONFORMANCE.md`'s multicast tests have run against the built mechanism — not before.
10. **The crate's store is the authority on a peer's liveness, and the provider mirrors it on a local cadence** (added 2026-09-25, PR #112's last blind review). The crate reports a record once and then only refreshes its expiry silently; the provider forgets an observation 120 s after its last push. With rule 3's 90 s query interval a live peer's record never lapses in the crate, so it is never re-reported, and a provider fed by discovery events alone forgets a peer that is still there — before the clamp, the 300 s interval let the record lapse and be rediscovered, which hid the gap. The refresh lives in the DRIVER, not in the crate's event stream and not in the provider's TTL: every half observation TTL (60 s) the driver re-pushes what the crate still holds, read through the additive accessor rule 8 names, and the provider's existing dedup extends each observation's expiry (it emits nothing for a refresh that is not due). The rate is a local timer over a store rule 2 caps, so it is bounded and not remote-fed. Two alternatives declined: the crate re-reporting each refresh as an event — a remote-fed rate an announcer sets, one event per record per second at worst; and a longer provider TTL — which delays forgetting without ending it and weakens expiry for every other provider.

## Alternatives considered

**A wrapper bound without vendoring** — `MdnsScope` counting records and replacing the inner behaviour at a cap — was the other route named on 2026-09-25 and lost on three counts: it cannot see the two per-interface buffers at all, it throws away every expiry event with the behaviour it replaces, and it gives the crate's failures no path out, so the degraded signal would still have to be inferred from silence, which an empty LAN also produces. **Refusing unsolicited responses** would bound the flood at the door and was rejected because it is the protocol: gratuitous announcements are how a peer that comes up second learns of the first. **Leaving the exception open** — the mechanism gated off, an operator who enables it accepting the exposure — is the interim state and not a destination: CLAUDE.md §6 admits an unbounded structure only with an amendment and adversarial coverage, and the amendment was written as time-boxed. **An upstream fix** is worth proposing from the patch once it holds, and is not waited for: the pinned release is what this repository ships. **Writing an mDNS behaviour of this repository's own** re-opens every question the crate already answers (the DNS codec, interface tracking, the query timer) for three caps and an event.

## Consequences

The repository owns a second tree it did not write — 13 files, some 1,900 lines of Rust — differing from upstream by the recorded diff and nothing else, and the maintenance contract is the same as ADR-0051's: reviewers audit `INTERWEAVE.patch`, not the tree; a libp2p bump re-vendors and re-applies; Dependabot and `cargo-deny` do not see the crate and `check_vendored_advisories.sh` does. A flood on the multicast domain now costs this node at most the caps' memory, linear CPU per packet and one response per second per interface, and is visible as counters. What a hostile LAN can still do is evict legitimate records by keeping the store full; discovery on such a LAN degrades to what the provider already saw, which is the intended loss and is what the counters show. `providers/mdns.md` states the bounds and the degraded signal; `DISCOVERY-CONFORMANCE.md`'s exception reads as closed by this record once rule 9 is met; `resource-limits.md` carries the numbers.

## Security implications

The invariant: a host on the multicast domain can spend a bounded amount of this node's memory and CPU and cannot use this node as a multicast amplifier. Rules 2 and 3 bound memory and make the bound un-outlivable by TTL; rule 4 bounds what this node sends in reply to what it receives; ADR-0052's boundary at the learn site and `MdnsScope`'s two closed doors keep every record short of a socket or a book. Residual risk accepted: on a hostile LAN, legitimate records are evicted under flood and LAN discovery stalls for its duration — a denial of LAN discovery to a node that has chosen to enable it on that LAN, not a denial of the node. The patch adds no code path a remote host reaches that the crate did not already have; it narrows three.

## Operational implications

Nothing is configured: the caps are constants and the once-per-second rule is the protocol's. An operator who enables `mdns` sees the drop counters rise on a flooded LAN and `MdnsUnavailable` or the interface-failed mapping when an interface cannot bind, join, send or receive — the degraded signal the deadline's row 4 waits for. A rising eviction counter on a quiet LAN means a cap sized wrong, which is a revisit condition below.

The flood harness and the cap assertions in `crates/transport/libp2p/tests/`; the drift check of rule 2's constant against `crates/discovery/mdns` beside the existing batch-bound check; the counters on the runtime handle; the runtime's mDNS arm surfacing `InterfaceFailed` and `WatcherFailed` as `SwarmEvent::MdnsInterfaceFailed` and `SwarmEvent::MdnsWatcherFailed`, and Stage 12's composer setting the provider's degraded state from them; the dead-watcher stop (rule 5) on PR #112 with the test that ends a watcher through the exported `Provider` seam; in the next mDNS change, the live-records accessor (rule 8), the driver's 60 s refresh (rule 10) and the behaviour rebuild on `MdnsWatcherFailed` (rule 5) by re-running `mdns_driver::build_behaviour`, each with a test that advances the clock or ends a watcher — and, in the same change, the two places that still teach the record's retracted wording: `mdns_bounds.rs`'s header and assertion note ("not reachable while that rule holds") and the vendored `behaviour.rs`'s comments that recovery "rebuilds the behaviour" (`:243-246`, `:745-747`); the 90 s default query interval with its `validate` bound below the clamp. All p2p-network-dev's, on their branch, in rule 9's order; this record is the caller and lands on that branch ahead of the patch.

## Revisit conditions

Drop the patch, and the `[patch.crates-io]` entry with it, when a crates.io `libp2p-mdns` release carries its equivalents — caps on the three stores, the once-per-second rule, an interface-failure event. Reopen rule 2's numbers if the eviction counter rises on a LAN that is not under flood (the cap is below a real LAN's population), or if the provider's own constants change (the drift check says so). Reopen rule 2's shape if refused records are measured displacing admitted ones — the eviction counter rising together with the boundary's refusal counter — since the remedy, refusing at the crate what the boundary will refuse, is a class predicate inside the crate and a rule 8 amendment. Reopen rule 3 if the provider's observation TTL changes meaning. Reopen the whole record if a libp2p major bump reshapes the crate so the diff no longer applies, or if the repository's dependency policy comes to cover path patches. Rule 5's spin condition is spent: the stop was built on PR #112 (a0dfc1d7), so there is no spin to measure; reopen rule 5 instead if the rebuild, once built, is found to lose records or interfaces across the swap.
