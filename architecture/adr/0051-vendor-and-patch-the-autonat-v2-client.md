# Vendor libp2p-autonat and give its v2 client a re-test entry point

**Status:** Accepted

## Context

ADR-0035 labels a direct address `verified_public` only on fresh evidence from **multiple distinct authorized AutoNAT v2 servers**, and states why: "reducing dependence on one lying/misconfigured observer". `architecture/transport/libp2p/AUTONAT.md` §5 adds that a verified state "must not survive beyond its evidence TTL without refresh". Both are accepted, both are security or liveness properties rather than tunings, and the standard-v1 client cannot deliver either.

The reason is the candidate lifecycle in `libp2p-autonat` 0.15.0's v2 client, measured on 2026-09-09 by reading the crate rather than its documentation. Line numbers throughout cite the PRISTINE 0.15.0 release, not the patched file now in tree, whose later lines have moved. Its tick sweeps only candidates whose status is `Untested` (`v2/client/behaviour.rs:319-321`). Issuing a probe sets `Pending` and asks one randomly chosen dialled server (`:297-300`, `:340`). A received dial-back sets `Received` (`:166`); a server's "not reachable" sets `Failed` (`:232`). Only `UnsupportedProtocol` and `Io` go back to `Untested` (`:212`, `:223`). Re-reporting an address only raises its score — the entry is never removed and its status never changes (`:108-112`). Two paths also leave a candidate `Pending` for ever with no event: a server reporting success when no dial-back arrived (`:186-198`), and a request dropped because the handler's ten-slot request map was full (`v2/client/handler/dial_request.rs:99-113`) — after the status was already set. The one public mutator, `validate_addr`, is `#[doc(hidden)]` and only *sets* `Received` (`:364`). **Once an address has been tested, no public path tests it again.** So an address is probed at most once, by one server, for the life of the process: the reachable-observer count for it can never exceed one, `required_distinct_successes: 2` is unreachable, and there is no refresh. Upstream `master` carries the identical lifecycle and 0.15.0 is the latest release, so there is nothing to wait for.

The crate's design goal is different from this repository's: it confirms an external address once for the Swarm's address book. This repository maintains a TTL'd, multi-witness verdict. Three facts bound the answer. Everything a separate client would reuse — the codec, the request and response types, the dial-back helpers, `Nonce` — is `pub(crate)`. A behaviour cannot be rebuilt inside a running Swarm: a fresh one has an empty `peer_info`, filled only by `ConnectionEstablished` events that have already fired, so it never learns that any peer is a server. And `deny.toml` forbids git dependencies, so a patched upstream cannot be depended on until it is released.

Two mechanisms already exist for what follows. `tools/checks/license_exempt.txt` is the recorded-provenance path CLAUDE.md §8 names for third-party material, deliberately empty until now. And a `[patch.crates-io]` entry with a `path` source resolves under `cargo-deny`'s sources policy, which bars registries and git and not paths — verified on 2026-09-09 against this workspace before this ADR was written.

## Decision

1. The workspace builds `libp2p-autonat` from `third_party/libp2p-autonat/`, the 0.15.0 crates.io tarball (sha256 `fab5e25c49a7d48dac83d95d8f3bac0a290d8a5df717012f6e34ce9886396c0b`), selected by a `[patch.crates-io]` entry in the root `Cargo.toml`. The version stays `0.15.0`, which is what lets Decision 7's guard ask the registry about the same release — not what lets `cargo-deny` see it, since it cannot (Consequences).
2. The copy is the tarball minus its packaging files (`.cargo_vcs_info.json`, `Cargo.toml.orig`, `Cargo.lock`; `.cargo-ok` is cargo's own extraction marker under `registry/src/` and is not in the tarball at all), plus the upstream `LICENSE` and one recorded diff, `INTERWEAVE.patch`. **Nothing else differs**, and the diff is the whole of what this repository owns in that tree.
3. The patch has two coupled halves and nothing else. `Behaviour::retest(&Multiaddr) -> bool` returns a known candidate to `Untested` and reports whether anything changed; it decides nothing about *when*. It resets a `Pending` candidate too, which is how the two stuck-`Pending` paths above are recovered. Because that orphans an in-flight nonce, the second half makes `reset_status_to` report whether a candidate still held the nonce and has the `AddressNotReachable` arm decline to emit when it did not — that arm is the only one which falls through to `GenerateEvent` *unguarded* — the success arm falls through too, behind its `received_dial_back` check. **A probe `retest` abandons therefore produces no `Event` at all**, which is what lets a caller attribute every `Event` to the probe it last started — with one precondition the caller owes, since `Event` carries no nonce: an outcome already queued in `pending_events` reaches the application on a later poll, so a `retest` between those two moments still delivers the stale one. Drain the behaviour's events before re-testing. That property rests on review of the recorded diff rather than on a check, and the reason is narrower than an earlier draft said. A probe in flight cannot be SYNTHESISED from outside: `handler` is a private module and `dial_request` is `pub(crate)`, so no test can inject `ToBehaviour::PeerHasServerSupport`, and without it the server pick returns `None`. It can be CAUSED: this crate also ships `v2::server::Behaviour`, reachable as `libp2p::autonat::v2::server`, so a two-Swarm test over real sockets — the shape `tests/connectivity/` already uses — would negotiate a genuine dial request and produce a real `Pending` candidate with a poll loop the test controls. **That test is owed, and it belongs to the step that constructs these behaviours rather than to this decision, which constructs nothing.** Saying the test was impossible would have told that step's author not to try.
4. Deciding when an address is re-tested — refresh while verified, a further observer until the threshold is met, retry after a failure under the dial gate's retry constants — is the `ReachabilityManager`'s (`crates/transport/runtime/src/reachability.rs`, landing on PR #84), keyed on the evidence `AUTONAT.md` §4 describes, and applied by the libp2p adapter calling `retest`. The crate's own tick and `with_max_candidates` remain its first-test sweep and its per-sweep ceiling.

   **`AUTONAT.md` §4 states three bounds and the crate supplies a lever for one of them, so the mapping is recorded here rather than left for the adapter to discover.** Naming `with_max_candidates` alone would be the same mistake this repository already made once for relay, where `RELAY.md` §8's budgets are not the crate's defaults in any row that matters.

   | `AUTONAT.md` §4 bound | Value | What the crate offers |
   |---|---|---|
   | max candidate addresses per cycle | 4 | `Config::with_max_candidates`. **The default is 10**, so an adapter that does not set it probes two and a half times the ceiling. `untested_candidates()` ends in `.take(max_candidates)`, which is what makes this the per-cycle number. |
   | max probes in flight | 2 | **Nothing.** `Handler::new` fixes it at `FuturesMap::new(Duration::from_secs(10), 10)` (`v2/client/handler/dial_request.rs`) — ten per connection, no field and no setter. The ceiling is the manager's to enforce by how many addresses it re-tests, or it is not enforced at all. |
   | probe timeout | 15 s | **Nothing, and it is moot.** The same line fixes the per-request timeout at 10 s. Stricter than the configured value, so it breaks no bound; it does mean the configured number describes nothing. |

   **Two of those three keys are therefore OWED A REMOVAL, and this is an obligation rather than a report.** `max_inflight_probes` and `timeout` are present in `AutonatClientConfig`, in `config.schema.yaml` and in `examples/connectivity-infrastructure.yaml` as this decision is accepted, and nothing reads either: a schema that documents a knob no mechanism can honour is a drift check waiting to fail. They must go, together with THREE restatements that present them as defaults: `AUTONAT.md` §4's two client rows, `CONNECTIVITY.md` §22's in-flight row, and `docs/architecture/resource-limits.md`'s client row — which §22 points the reader at, and which also states a ceiling of 8 that the shipped client exceeds and an overflow of "defer next probe cycle" that is really a silent drop. **THREE SERVER LOOK-ALIKES MUST SURVIVE**, and naming one of them was not enough -- this list has twice been corrected for enumerating a single look-alike. They are `AUTONAT.md` §7's `probe timeout: 15 seconds` under its Default limits, `CONNECTIVITY.md` §6's `probe timeout: **15 s**` under the server role, and the `timeout: duration[5s..60s] = 15s` under `transport.connectivity.autonat.server` in `config.schema.yaml` with its example counterpart -- which sits SIX LINES below the client key this decision orders removed and is byte-identical to it. Disambiguate by the block, never by the string. What survives is `max_candidate_addresses_per_cycle`, because it has a lever. An earlier draft of this paragraph said the removal had already happened on another branch, which coupled an accepted decision to the content of an unmerged diff and was falsified by three files in this tree.
5. Every file under `third_party/libp2p-autonat/` is listed in `tools/checks/license_exempt.txt` with licence, copyright holder, upstream version and tarball checksum. `third_party/README.md` carries the table of what is vendored and why. `LICENSE` is the one file the checksum does not cover, because the crates.io tarball does not carry one; it is fetched from the upstream repository and is excluded from `INTERWEAVE.patch` by name, so a byte-equality guard must special-case it.
6. `third_party/` sits alongside the landing zones ADR-0045 enumerates without being one for first-party code, and `README.md`, `IMPLEMENTATION.md` and `CLAUDE.md` §1 each describe it. Guards that decide whether FIRST-PARTY code is wired exclude it, on the same reasoning that excludes `spikes/`: a vendored dependency is evidence of nothing about this repository's own code and must never vouch for it. Guards that ask what the shipped binary CONTAINS do not exclude it, because a `[patch.crates-io]` tree is compiled in and is editable here.
7. `tools/checks/check_vendored_advisories.sh` restores the advisory coverage the patch removes. For every crate this workspace builds from a local tree it resolves that crate at its declared version from the registry and runs the advisory check there, under this repository's own `deny.toml`. THREE sources say what that set is, because each sees what the others miss: the package graph, every manifest under `third_party/` at any depth, and every `path` a `[patch.*]` table declares — in the manifest, `.cargo/config.toml`, or the legacy `.cargo/config`, since cargo omits an unused patch from the graph wherever it was declared. They must account for each other, and THREE conditions are a refusal rather than a pass, because a sweep that could not ask is not a clean one: a shipped tree the package graph does not name, a local crate with no registry release at its declared version, and a local tree OUTSIDE this workspace root, which none of the three sources can reach. **What the set can still MISS is a different question and must not be read off that list**: a crate vendored INSIDE a first-party landing zone and left a workspace member is skipped, and reached as a plain path dependency it appears in none of the three. That is inherent to a name-based rule rather than a defect in one, and Decision 6's convention plus the licence-exemption list are what stand there. An earlier draft called the out-of-root path "the one shape none of them can ask about", which named the REFUSED shape as the unique gap and left the silent one unstated. It is the only warning a vendored tree will get, since neither `cargo-deny` nor Dependabot sees one.
8. The patch is dropped, and the `[patch.crates-io]` entry with it, when a crates.io release of `libp2p-autonat` carries an equivalent re-test path. Until then every libp2p version bump re-applies the diff to the new tarball and re-records the checksum.

## Alternatives considered

**Amending ADR-0035 to a single observer** was the cheapest and was rejected: the multi-observer rule is stated as a security property against one lying observer, and weakening it to fit a library inverts the source-of-truth order. It would also not restore refresh, leaving `verified_public` a fifteen-minute window after startup — which relay reservation targets and the connectivity summary are keyed on. **Writing an independent v2 client** would give full control of the lifecycle but, with the codec `pub(crate)`, means a second protobuf pipeline and roughly nine hundred lines of handler beside the server's copy of the same wire code, re-opening every question the crate already answers (nonce handling, amplification bounds, stream-upgrade errors) for a one-method defect. **Waiting for upstream** has nothing to wait for: `master` is identical and no newer release exists. **A git dependency on a patched fork** is barred by `deny.toml`, for the reasons that file records: no version, no yank mechanism, no advisory database. **Rebuilding the behaviour periodically** fails on `peer_info`, above. **Vendoring only the client module** fails on visibility: it would have to carry the protocol and generated code too, duplicating the server's wire code inside one binary.

## Consequences

The repository owns a tree of some 6,400 lines it did not write, differing from its upstream by two coupled hunks and their comments, and the maintenance contract is the diff: reviewers audit `INTERWEAVE.patch`, not the tree. A libp2p version bump now includes re-vendoring the matching `libp2p-autonat` tarball and re-applying the patch, a step Dependabot cannot do and will not prompt for, since a path-patched crate is invisible to it. **`cargo-deny` cannot see it either**, which an earlier draft of this decision got wrong: a path-patched crate has no `source` and no `checksum` in `Cargo.lock` and the advisories check skips it. Measured with `atty 0.2.14`, which carries RUSTSEC-2021-0145 and RUSTSEC-2024-0375 — as an ordinary dependency `cargo deny check advisories` fails on both, and path-patched to a copy of the same source it prints `advisories ok`. So vendoring removes a crate from advisory coverage entirely unless something replaces it, which is why Decision 7 exists. `ReachabilityManager` (`crates/transport/runtime/src/reachability.rs`, landing on PR #84) gains a scheduling role this ADR makes legitimate: an earlier draft of that module scheduled probes, and PR #84 removed it precisely because no lever existed. `retest` is the lever, at address granularity, with a completion event for every probe that COMPLETES — and it is also the recovery for the two paths above that never complete at all, which a caller reaches by its own timeout rather than by an event. Server choice stays the crate's random pick among dialled connections, so a second distinct observer is probabilistic: with *n* dialled servers the chance that *k* consecutive probes land on one is *n*^-(k-1), and the manager counts distinct servers, so convergence is expected rather than guaranteed per probe. **One asymmetry `retest` exposes and does not close.** The client pushes `ToSwarm::ExternalAddrConfirmed` on a success (`v2/client/behaviour.rs:201-202`) and never emits `ExternalAddrExpired` — harmless upstream, where an address is tested once. Under `retest`, an address confirmed once and failing later stays in the Swarm's external-address set and so keeps being advertised by Identify, while this manager's own verdict expires on schedule. `AUTONAT.md` §5's "must not survive beyond its evidence TTL" therefore holds for the verdict and not for what the node advertises. Withdrawing the Swarm-level address is the adapter's to arrange in step 3, and is called out here because nothing in the crate will do it.

The spike harness at `spikes/spike-004/harness/` has its own workspace and is unaffected; its measurements describe upstream, which is what they should describe.

## Security implications

The property this exists to preserve is ADR-0035's: one observer cannot make an address `verified_public`. Under this decision the manager counts distinct servers, and a server cannot arrange to be counted twice because it does not choose itself — the crate draws the server at random from connections this profile dialled. The patch widens no attack surface reachable from the network: `retest` is called only by first-party code and reads only local state, and a late outcome for an orphaned nonce is refused on every path (a dial-back with an unknown nonce is rejected by `on_connection_handler_event`; `UnsupportedProtocol` and `Io` return without emitting; a success is dropped by the `received_dial_back` guard; and `AddressNotReachable` is declined by the patch's second half). The converse holds with one exception, recorded on the method: `validate_addr` — upstream's `#[doc(hidden)]` test-only hook, which nothing in production calls — also overwrites a nonce, and calling it on a pending candidate would swallow that probe's genuine failure. **What the patch does remove is an absolute bound**: upstream probes each candidate at most once, so total probe volume over a process's life is capped by the candidate count. Under `retest` the bound becomes a rate — the crate's tick, `probe_interval`, times `max_candidates` per sweep (Decision 4) — and each probe costs an authorized server a dial-back and 30–100 kB. Nothing external can call `retest`, so this is a self-inflicted-load bound rather than an attack surface, and it is the manager's schedule that must respect `AUTONAT.md` §4's cadence. Supply-chain exposure changes shape rather than size: the vendored tree is pinned to a checksum recorded in two places and differs from the registry by an auditable diff, which is a stronger statement than a registry dependency makes; the cost is that the tree no longer moves with upstream security fixes until someone re-vendors, and the residual risk accepted is exactly that lag, bounded by the revisit conditions below.

## Operational implications

Nothing is configured. An operator observes `autonat_retests_total{reason}` — added to `AUTONAT.md` §9's required diagnostics by this decision, with reasons `refresh`, `second_observer` and `retry` — and a direct address reaching `verified_public` at all is the visible difference. If the patch were silently lost — a re-vendor that forgot it — the symptom is a profile that never leaves `unknown` or `not_verified` with servers answering correctly; `crates/transport/libp2p/tests/autonat_client_retest.rs` fails on that before it ships.

## Implementation implications

`third_party/` is a new top-level directory, a landing zone ADR-0045 did not enumerate and which this ADR adds with one rule: a subdirectory without `license_exempt.txt` entries is an unreviewed import. For a Rust tree that rule is mechanical — the vendored `.rs` files carry no SPDX line, so every one of them fails `check_license_headers.sh` unexempted — but it is not self-enforcing for every shape: a vendored tree of only Markdown, TOML and `.proto` files would pass unexempted, because those extensions require no header. Vendoring one of those is where a reviewer, not a script, has to apply this rule. The `[patch.crates-io]` table lives in the root `Cargo.toml` with a comment naming this ADR. The test for the method lives in `crates/transport/libp2p/tests/`, the lowest layer that can see both the vendored crate and the workspace's libp2p features; the vendored crate is not a workspace member, so its own test suite does not run here. Stage 11 step 3's adapter is where `retest` is first called, under the manager's three reasons; until then the method is built and tested and used by nothing, which `check_domain_fns_are_called.sh` does not govern (it is not a first-party domain function). Filing the patch upstream is part of this implementation, so the exit condition in Decision 8 can arrive. One follow-up is named rather than built here: a guard that asserts `third_party/libp2p-autonat/` equals the recorded tarball plus `INTERWEAVE.patch`. It needs the pristine tarball available to CI and must special-case `LICENSE` per Decision 5, so it is more than a grep — and until it exists, the tree's integrity rests on review of the recorded diff rather than on a check. And a path dependency does not receive `--cap-lints=allow` as a registry crate does, so warnings from the vendored tree now reach this workspace's build output and a future toolchain can add more; today there are none, and the answer if that changes is a `[lints]` allow in the vendored manifest rather than edits to its source.

## Revisit conditions

Drop the patch when a crates.io `libp2p-autonat` release exposes a re-test path or a candidate lifecycle the manager can drive directly. Reopen this ADR if a libp2p major bump changes the v2 client's candidate model so the diff no longer applies cleanly; if `cargo-deny` or the repository's dependency policy changes to cover path patches; if ADR-0035's observer requirement is itself revisited; or if the probabilistic second observer measurably fails to converge on the real-NAT matrix SPIKE-004 phase B still owes — the measurement that would say so is the distribution of `autonat_retests_total{reason="second_observer"}` against servers dialled.
