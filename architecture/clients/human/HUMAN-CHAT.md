# HumanChatV1 application envelope

Status: **first-party application protocol design; not part of transport v2**.

The desktop and Android human clients need an interoperable text-message envelope while the generic transport remains payload-agnostic.

## Media type

```text
application/vnd.interweave-human-chat+json;v=1
```

## Envelope

Conceptual canonical fields:

```text
{
  "v": 1,
  "kind": "text",
  "app_message_id": "<32 lowercase hex chars = 16 bytes>",
  "text": "<UTF-8 text>",
  "reply_to": "<app_message_id>?",
  "sent_at_ms": <diagnostic integer?>,
  "from_endpoint": "<EndpointId>?"
}
```

Rules:

- UTF-8 JSON, bounded so the encoded payload remains <= the transport effective payload limit;
- `app_message_id` is exactly 16 CSPRNG-generated bytes encoded as **32 lowercase hexadecimal ASCII characters** (`^[0-9a-f]{32}$`); uppercase, prefixes, separators, other lengths and non-canonical encodings are invalid. It is application reply/retention identity, not DirectMessageV2 dedup identity;
- `reply_to`, when present, uses the same canonical 32-lowercase-hex grammar. The referenced message does **not** need to exist locally; an unknown reference does not reject the envelope or trigger network lookup, and the UI may render a neutral `Referenced message unavailable` placeholder;
- `sent_at_ms`, when present, is an integer Unix-epoch millisecond value in `0..253402300799999` (through `9999-12-31T23:59:59.999Z`). Values outside that closed interval are malformed. An in-range value is display/diagnostic only and never trust/replay/freshness/order authority; receivers may suppress or annotate implausible display times without changing transport/application acceptance;
- direct transport metadata is authoritative for `source_peer` and peer-asserted `source_endpoint`; any conflicting application `from_endpoint` is ignored for routing/authority;
- on broadcast, `from_endpoint` is an explicitly **unauthenticated display hint** because transport broadcast origin is PeerId-only;
- unknown fields are ignored for forward compatibility within v1 bounds;
- active markup/script is not supported; `text` renders as plain text;
- attachments, edits, reactions, typing indicators, delivery/read receipts, and multi-device sync are not part of HumanChatV1.

A later richer chat protocol can version independently of transport.

## Retention semantics

HumanChatV1 contains **no sender-controlled persistence field**. Retention is purely local receiver/application state under [`RETENTION.md`](./RETENTION.md) and ADR-0044.

- outbound HumanChatV1 content may be retained locally only while transport-pending;
- inbound HumanChatV1 content is retained unread until local read state;
- after read, only an explicit local receiver `Keep` action makes the inbound content durable;
- `from_endpoint`, `reply_to`, unknown extension fields, message text, or any future remote field cannot request/force retention;
- local read/Keep state is not serialized into HumanChatV1 or sent back to the peer in v1.

A future protocol that requests retention, provides receipts, or synchronizes history requires a new application-protocol version/ADR rather than an ignored v1 extension convention.

## Fixture cases

Phase-1/application fixtures include at least:

- valid ID: `00000000000000000000000000000000`;
- invalid IDs: uppercase hex, 31/33 characters, `0x` prefix, hyphenated UUID form and non-hex text;
- valid diagnostic timestamps `0` and `253402300799999`; values outside that closed interval are rejected as malformed HumanChatV1 metadata;
- `reply_to=11111111111111111111111111111111` with no matching local message remains a valid inbound message and renders without lookup/rejection.
