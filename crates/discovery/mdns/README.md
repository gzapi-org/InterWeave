# mdns

MdnsDiscovery implementation.

**Current status:** Stage 9, active workspace member. The normalization half of LAN discovery: raw `(peer, address)` observations pushed in by the backend become bounded, validated candidates. **This crate owns no socket** — the multicast mechanism is a libp2p behaviour in `crates/transport/libp2p`, because only that crate may own a Swarm.

Any host on the multicast domain can advertise, so mDNS grants **zero trust** and every bound is applied before an observation is emitted. A peer string outside the identity grammar is dropped, not repaired. A network that blocks multicast makes this provider *degraded*, never fatal, and leaves the other providers untouched.

**The multicast backend EXISTS since 2026-09-20**, in `crates/transport/libp2p` — the `mdns` field and its switch, the driver applying ADR-0052's boundary at the learn site, and the two events a composition root pumps back in here. The owner ordered it built (plan §14, `DISCOVERY-CONFORMANCE.md` Decision 2026-09-20). The blocker used to be a dependency advisory, and the history is kept because that retired blocker is the one a reader remembers: enabling libp2p's `mdns` feature pulled `hickory-proto 0.25.x` with RUSTSEC-2026-0118 (the advisory said "no safe upgrade", which was about the 0.25 line it named — 0.26.1 carries the fix) and RUSTSEC-2026-0119, which `tools/checks/check_dependencies.sh` refused. The `libp2p 0.57` bump has since been taken: the graph is `libp2p-mdns 0.49` on `hickory-proto 0.26.3` and the advisory check is clean, so **no dependency is waiting on anything**. This crate is complete without the socket — observations arrive through `push_discovered`/`push_expired`, which is how they were always going to be tested. **What has never happened is a packet**: the multicast conformance tests need an environment whose multicast behaviour is chosen and measured rather than inherited, which is SPIKE-010, and until its node rows run and are recorded the stage record reads TAKEN-NOT-MET. A profile that sets `enabled: true` on an `mdns` provider is still **refused at validation**, the same way an enabled `kademlia` entry is, and for the same reason as Kademlia now: nothing composes the provider with the backend yet (plan §15), so enabling it would start a healthy-looking provider that receives nothing (`architecture/discovery/PROVIDER-CONTRACT.md`). That refusal lifts at the composition root, with Kademlia's.
